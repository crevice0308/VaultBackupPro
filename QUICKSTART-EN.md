# VaultBackup Pro 1.3.0 — Quick start

Install one VaultBackupPro-1.3.0.jar in plugins while the server is stopped. Do not extract the JAR or keep another VaultBackup version beside it. Use Java 25 and Paper, Purpur or Spigot for Minecraft 26.2 or newer; Folia and other regionized servers are not supported. The JAR is built directly from the published source and is not obfuscated. Backups and the state directory of 1.2.x are used as they are, and config.yml needs no changes. This is a prerelease: no real-server test was run for 1.3.0, and the real-server results recorded for earlier releases do not cover it. Read TEST-RESULTS.md for what was tested and what was not.

Japanese is the default. Set language: en_US in plugins/VaultBackupPro/config.yml and use /backup reload for English. Existing configurations are preserved. A helper for an already-reserved restore keeps the language recorded when that job was created.

Create: /backup create optional-label. List: /backup list. Status: /backup status. Verify: /backup verify re-reads every archive, while /backup list verifies only archives that are new or changed. The /backup GUI provides the same administrator actions. Only players, the console and RCON can run /backup; command blocks are refused, and a sender without any VaultBackup permission does not see the command. Actions are written to the server log with the sender's name. The commands that change settings are refused while config.yml holds hand edits that have not been applied; run /backup reload first.

A backup of a running server continues when files change underneath it. A file that keeps changing while it is copied is stored as last read, and the number of such files is shown in the result, the list, the GUI and the log; those files may be internally inconsistent. Paths that cannot be backed up (symlinks, special files, unreadable folders, names that cannot be stored) refuse the whole backup and are reported together. Free space is checked before anything is written. On a system started without a UTF-8 locale, a file with a non-ASCII name refuses the backup, and a warning is logged at startup.

Automatic backups count their interval from the newest backup, also across restarts. Without any backup, or when one is already overdue at startup, the first one runs about two minutes after startup.

Delete: /backup delete <id> immediately deletes the target without another confirmation. This is irreversible, including the final backup. Automatic retention may also remove the final archive to satisfy a positive capacity limit. A retention count/byte value of 0 disables that limit; it does not request deletion of everything. An archive that failed verification is listed separately and can be removed with /backup delete <id>. Keep independent recovery copies.

Restore: /backup restore <id> verifies the archive and directly reserves it for your next normal server stop. There is no second confirm command. The reservation is refused up front when the server root is a mount point, when its parent folder is not writable, or when there is not enough free space beside it. Keep playing until you are ready, then perform a normal stop. Disable host auto-restart. Wait for the helper's SUCCESS, its process exit, and the recorded result before manually starting the server. /backup restore cancel cancels a reservation before application; wait for the acknowledged cancellation message. Do not interpret CANCEL_PENDING as completed cancellation. /reload or a plugin reload also cancels the reservation; the server keeps running.

Paper and Purpur confirm through the server API that the server is stopping. Spigot has no such API: there, a JVM exit within 10 minutes after the plugin was disabled counts as a normal stop. On Spigot a reserved restore can therefore also be applied when only the plugin was disabled and the server then terminated abnormally within those 10 minutes. Do not reload or disable the plugin while a restore is reserved.

The helper log and status file are shown by /backup status. By default they are in ../VaultBackup-state/restore-jobs/<job-id>/helper.log and status.properties relative to the server root. Do not share job.properties; it contains authentication material. A live backup cannot make unrelated plugins or external databases transactionally consistent.

A reservation left waiting from an earlier run is cancelled at startup while the root guard is retained. At startup the plugin requests a server stop only when another process holds the root guard or a restore journal exists; other startup problems disable only the plugin. An actual restore conflict or evidence of an incomplete replacement cannot safely permit ordinary world startup. This edition removes redundant interaction steps, not authorization, archive integrity checks, or the requirement to restore offline.

Verification scope: this release targets Paper, Purpur and Spigot for Minecraft 26.2 and newer on Java 25. The build compiles and link-checks the plugin against the Spigot API 26.2 and 26.3 and the Paper API 26.2 and 26.3; versions newer than 26.3 run with a warning. No real-server test was run for 1.3.0, because starting a server requires accepting the Minecraft EULA. The real-server results in docs/RUNTIME-TEST-RESULTS.md and docs/test-evidence belong to earlier, obfuscated builds and do not cover 1.3.0. Spigot at run time, Windows and real-client GUI interaction remain unverified. PaperMC ended support for 26.2 on 2026-11-03, so 26.3 is recommended. See TEST-RESULTS.md and release/SHA256SUMS.txt for the build results and the final artifact hashes.

Prerelease test build: verify backup and restore on a test server before production use. Concurrent startup during restoration is unsupported. In the 1.2.0 real-server tests Paper wrote world files after the plugin requested shutdown on a guard conflict; this was not re-tested for 1.3.0. Disable host auto-restart and do not start until the restore helper has completed and exited. This plugin cannot guarantee prevention of corruption caused by a simultaneously started server.
